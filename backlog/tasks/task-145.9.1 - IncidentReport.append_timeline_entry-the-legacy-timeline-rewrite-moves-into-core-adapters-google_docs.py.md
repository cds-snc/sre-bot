## 2. Decisions this plan takes (each flagged where it is a ruling)
D1 Port shape (OQ3 approved: UNSUPPORTED_OPERATION with the cause in the message, documented on the Protocol method; no later row needs severity or link-less entries in the document: incident-management.md:73-79, the timeline's end home is records, TASK-147), built for TASK-145.9.2 so it reverts nothing: IncidentReport gains
  async append_timeline_entry(report: ReportReference, entry: TimelineEntry) -> OperationResult[None]
  async remove_timeline_entry(report: ReportReference, message: MessageReference) -> OperationResult[None]
 No new domain type: 145.9.2 already builds a TimelineEntry (kind message, source_message, captured_entry_id) for TimelineStore.append and passes the same entry here. The report's identity of an entry is its permalink (channel + full ts, #1858 (b)), so append requires kind MESSAGE and entry.source_message.url; anything else (manual entry without a message, a severity_changed entry, no url) is PERMANENT_ERROR UNSUPPORTED_OPERATION with the reason in the message (no other registry code fits; OQ3). Removal takes the message, needs its url the same way, and an entry not in the document is success (idempotent, like archive/join); the legacy handler keeps its own warning log through the pure function's None. A re-add of an entry already in the document is success with no write. Failures are exactly update_timeline_section's results (DOCUMENT_UNREADABLE transient for an unreadable or missing document, RANGE_NOT_FOUND when the headings are gone, TIMEOUT, HTTP_ERROR, ...); the port carries them unchanged, it does not reclassify (OQ4: a later behaviour slice may map a missing document to NOT_FOUND like the other methods).
D2 Legacy reaches the moved code on an allowed path, no provider and no Runner: the handlers are sync and call sync module functions in features.incident.core.adapters.google_docs, the same import the module already has (incident_conversation.py:13 for extract_google_doc_id, incident_document.py:16-22). That is migration.md rule 2 (modules may import features) and rule 5 (import repoint); no new import-linter edge, no ignore entry (contract (e) allows **.adapters.** -> integrations.**; contract (g) forbids only the reverse). The async port is for async consumers (145.9.2); a sync handler never awaits it, so outbound-clients.md 2026-11-18 (one asyncio.Runner per run at the edge) does not apply here: nothing sync consumes an async port in this slice. Each legacy edit is tagged TODO(TASK-145.9.2) (migration.md rule 1).
D3 One bounded recompute, not a retry: update_timeline_section keeps the bound of 3 writes (now the setting of D4) as the recompute bound, re-reads before every write, recomputes only on TIMEOUT or a HTTP_ERROR refusal whose re-read shows the revision moved, never sleeps, and is not wrapped in a retry helper (outbound-clients.md 2026-11-17). The adapter methods call it once inside one asyncio.to_thread (the whole bounded loop is one worker-thread unit, as write_draft_document already is; a sync loop of blocking reads and writes with no sleep, nothing awaits inside it).
D4 (human ruling 2026-11-18, OQ1) The recompute bound is a typed setting, not a constant: [incident_core] timeline_update_attempts (int, ge=1, default 3, the #1858 value) on IncidentCoreSettings (features/incident/common/settings.py, beside full_read_max_items) and in config/base.toml [incident_core] with a comment. update_timeline_section reads get_incident_core_settings().timeline_update_attempts at call time (no import-time read); the module constant TIMELINE_UPDATE_ATTEMPTS is deleted, not moved. Rule recorded in decisions/configuration.md (step 6): plain constants are avoided; a value is a typed setting with a default unless it must never change (a vendor or protocol fact such as a Slack text limit, a format or marker the stored documents depend on such as TIMELINE_START_HEADING), and such a constant states that reason. CONVERSATION_NAME_ATTEMPTS (core/domain.py:549) does not meet it: follow-up task, not this slice.
D5 One copy of the entry logic: the pure rewrites the handlers run in closures (dedupe by message key then append then chronological sort; span removal by key) and rearrange_by_datetime_ascending move into the adapter as pure functions timeline_with_entry(content, url, entry_line) -> str | None and timeline_without_entry(content, url) -> str | None, and both the handlers and the port methods call them. So the 11 pins exercise the code append_timeline_entry will run in 145.9.2. Extracted verbatim, behaviour-neutral. Alternative (leave the closures, duplicate ~35 lines in the adapter until 145.9.2 deletes the handlers) rejected: two copies drift during a slice that has a live consumer (OQ2).
D6 Start/end markers: the adapter's single definition becomes public TIMELINE_START_HEADING (renamed from _SRE_BOT_GENERATED_TIMELINE, google_docs.py:390 and :1453) with TIMELINE_END_HEADING = "Trigger"; incident_document.START_HEADING/END_HEADING are deleted (2026-11-05 comment #2).
D7 Fake: InMemoryIncidentReport holds a report's timeline as entries keyed (conversation_id, ts digits) so identity equals timeline_message_key(url); append dedupes, orders by posted_at, remove deletes by key, unknown report and other systems follow the existing fake rules. UTF-16: the parity test's Docs stub is the legacy FakeDocument (offsets counted in UTF-16 code units, assert on a non-BMP boundary, links kept) moved into the strict test zone; the fake at the Protocol level has no offsets, the parity assertion is that both implementations read back the same entries for text containing non-BMP characters.
Domain-model evolution gate: not applicable. No entity is added or reshaped (TimelineEntry and MessageReference are used as defined by TASK-145.8.1); the matrix/cardinality evidence is 145.8.1's. MessageReference.url stays "a hint" on the record; this port documents that the report needs it.
