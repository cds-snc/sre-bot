## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Behavior slice of TASK-64 (approved 2026-11-18). run_if_leased (infrastructure/coordination/lease.py) releases at job end, so a run shorter than the gap between two replicas' ticks lets the second replica run the same tick (the incident legacy upgrade dry run reported twice per interval, 0.7 s apart, 2026-11-17). decisions/reliability.md (2026-11-18) requires a minimum hold, ShedLock's lockAtLeastFor. Design (approved): hold = min(lease TTL, interval - [scheduler] lease_hold_margin_seconds, default 5), so a daily job holds its TTL and the TTL stays the maximum hold; new primitive ConditionalWriteStore.expire_at(key, claim_token, at) (conditional update under the claim token, never a delete; DynamoDB UpdateItem, already granted by IAM), LeaseStore.release(name, claim_token, *, not_before=), run_if_leased(..., min_hold=) holding after a short or failed run and releasing as today when the run ends past the hold. Applies to every Tier-2 job at once (TASK-64.1 put them all on the registry). TASK-145.9.2 and TASK-147.6 wait on it.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 ConditionalWriteStore.expire_at sets an in-progress claim held by the token to expire at the given epoch second, never deleting it; a stale token, a missing key or a COMPLETED key returns False and changes nothing; both stores pass the conformance suite for it (parent AC #6)
- [x] #2 LeaseStore.release takes not_before: a future instant keeps the lease until then through expire_at, None or a past instant deletes as today
- [x] #3 run_if_leased with min_hold keeps the lease until start plus min_hold after a run that ends earlier, including a failed run, and releases at end after a longer run
- [x] #4 The registry derives the hold as min(lease TTL, interval - [scheduler] lease_hold_margin_seconds) (daily: the TTL); the margin is a typed setting declared in config/base.toml with default 5; a leased interval at or under the margin raises ValueError at registration; the hold end is floored to the whole second, so it never passes the acquire-time TTL expiry
- [x] #5 A test runs a short Tier-2 job on two simulated replicas over one store, ticks about a second apart, and asserts a single run per tick across several ticks; a control without the hold runs twice per tick (parent AC #6)
- [x] #6 decisions/reliability.md states the hold formula, expire_at beside acquire and release, and a Checks line for the hold
- [x] #7 A held release for a token that matches no record (the TASK-100 fail-open lease) changes nothing and holds nothing, and the hold never exceeds the lease TTL

## Blast radius and rollback

Merging to main deploys, and it changes every Tier-2 job's lease behavior at once: provision_aws_identity_center (hold 1800 s of a 2 h interval), the stale-channel nudge and spending (daily, hold 1800 s), the incident legacy upgrade (hold 900 s of 30 min). Effect: a short run no longer lets the other replica repeat the tick; a restart or deploy inside the hold does not rerun the job until the hold ends (at most the TTL). Wrong hold: a job skips a tick (worst case until the TTL) or repeats (today's behavior); no data effect, bodies idempotent. A held release on the failing DynamoDB path raises like release does today. Access sync's platform lock is untouched (no min_hold). One `git revert` restores the old code; a lease already held by the new code expires by its own TTL or hold (at most 1800 s), so no cleanup, and the table schema is unchanged. No terraform, IAM (UpdateItem already granted), SSM or environment-name change, so deploy-checks are not required. No ordering constraint with other PRs.
