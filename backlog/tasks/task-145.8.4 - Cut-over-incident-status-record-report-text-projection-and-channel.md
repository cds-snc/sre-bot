## 2. Decisions (all proposed; reasons in the comment)

D3 set_status_text is `async def` on the IncidentReport Protocol (outbound-clients.md async-port rule), the Google adapter offloads its googleapiclient call with one asyncio.to_thread inside the method; TASK-145.8.8 converts the other five methods later (the port is mixed until then, listed in the Migration entry that already names it).
D4 Fan-out semantics (OQ2): the record write is the commit point. If it fails (conflict, unreadable legacy item, store error) nothing derived is written and the reply says so. A failure of report, projection or channel is logged (event per stage, error_code) and reported in the reply, and the remaining stages still run. A replay (status already stored) still runs the other three stages, which is how a failed report or projection stage is repaired (run the command again).
D5 Channel stage: no conversation on the record or conversation_is_writable false or its check failed -> stage skipped and reported (parent rule: an archived channel never blocks a record update).
D6 Report stage: no report reference on the record (legacy items without report_url) -> skipped and reported; the bookmark scan of the legacy code is not carried (incident-management.md 2026-11-05: report from the record, not the channel bookmark).
D7 Replies and the channel message go through an incident_response catalogue (en-US, fr-FR; i18n.md:23,29); the channel message uses the invoker's locale, so English is byte-identical to today ("<@U> has updated the incident status to X."). The service takes the notice already rendered, so L6a can pass its own modal wording.
D8 Status argument: exact match on the five IncidentStatus values (parity, case-sensitive); the invalid-status reply lists them from IncidentStatus; the hand-kept lists are deleted (valid_statuses deleted here, 145.12.1 ruling).
