## 2. Decisions (each judged against M2b-M4b)
D1 Legacy stays until M3 (CONTRADICTS the outline step 2 and AC#3's deletion clause). schedule_retro.py is live production until M3, so M2a cannot rewrite or delete insert_event, get_freebusy, generate_unique_id, public_holidays.get_federal_holidays or their tests (test_incident_core_calendar_adapter.py, test_incident_postmortem_public_holidays_fetch.py, test_incident_postmortem_slot_search.py, the pin). Deleting get_federal_holidays now would either break find_first_available_slot or force a production change to the live path (requests -> async httpx, retries, error behaviour), which is not dark. M2a ADDS the new classes beside the legacy functions; M3 deletes the legacy functions, generate_unique_id, get_federal_holidays, adapters/public_holidays.py, the requests_mock test and rewires the pin (they die with their last caller). Dead-code rule is honoured: nothing M2a touches is dead. Human ruling requested (OQ1); AC#3 is left as written and a comment on the task records the proposed wording.
D2 Free/busy is a SEPARATE port, CalendarAvailability, not a MeetingScheduler method. Reasons: (a) service-accounts.md:46 and rule 5 treat reading people's free/busy and writing events on the bot-owned calendar as different powers (people read/free-busy only); (b) TASK-181 narrows Calendar scopes per operation (events vs free/busy), so one adapter class per port declares its own scope constant (both keep today's CALENDAR_SCOPES value at google_calendar.py:22; TASK-181 narrows each); (c) M2b's domain needs only availability, M4b only the scheduler, so neither fakes the other's surface (interface segregation); (d) a free/busy check without booking is a plausible second use. Both adapters live in google_calendar.py; no extra file.
D3 The port is vendor-neutral and holds no policy: no requestId, calendar id, scope, reminder default, time zone default or Meet wording in the Protocol (outbound-clients.md: no vendor-only concepts through a vendor-neutral Protocol). A MeetingScheduler instance serves ONE calendar: build_meeting_scheduler(calendar_id) in core/api.py (plain function, like build_incident_store; the postmortem plugin passes [incident_postmortem] calendar_id in M3). Meeting ids are the vendor event id; M3 builds PostmortemMeetingReference(system, tenant, vendor_id=meeting id, url) with the tenant from ConfiguredSystems. Consequence: if the configured calendar id changes, stored references 404 and M4b's "missing" state offers a new booking.
D4 One idempotency source (extends the outline's "one requestId source"; OQ3). MeetingRequest carries a required caller-supplied idempotency_key (M4b passes its per-incident claim token; one key per booking attempt, never per slot, because a deleted event id cannot be re-inserted). The adapter derives from it, once, the client-supplied event id (lower-case base32hex of a SHA-256, 52 characters in a-v/0-9, within Calendar's 5-1024 rule) and uses the same value as conferenceData.createRequest.requestId. generate_unique_id is not reused. A 409 on create means the key was already used: the adapter reads that event and returns it (replay returns the same meeting); a 409 whose event is gone/cancelled is PERMANENT_ERROR with error_code "409". Writes stay one attempt (AC#1); restoring SDK retries on insert is left to TASK-87.3, which asked for this key to be settled with TASK-86 so there are not two keys per slot.
D5 get returns the event's CURRENT state: id, title, start, end (aware datetimes), status (CONFIRMED, TENTATIVE), url, video_url, attendees. A cancelled/deleted event (404, 410, or status cancelled, whose resource may omit times) is NOT_FOUND with ErrorCode.NOT_FOUND so M4b's "missing" has one branch and start/end are never optional. An all-day event (hand edit on the shared calendar) has no dateTime: PERMANENT_ERROR with INVALID_RESPONSE, logged. patch takes a MeetingChange of optional fields (title, description, start+end+time_zone together, attendees as the FULL replacement list because Calendar replaces arrays) and sends only what is set, sendUpdates=all, and returns the updated ScheduledMeeting; delete notifies attendees, 410 (already deleted) is SUCCESS, 404 is NOT_FOUND. An ended meeting is never patched or deleted: that is M4b's rule, not the adapter's. All three writes use num_retries=0 (AC#1; notification emails could repeat on an SDK replay); reads (get, free/busy) keep the factory's retries. Needs an outbound-clients.md Migration line (OQ5).
D6 Time: MeetingRequest and MeetingChange take aware datetimes and an IANA time_zone name from the caller (zone is the postmortem setting in M2b); adapter sends RFC 3339 dateTime with offset plus timeZone; no "America/New_York" or "EDT" constant, no display text (the legacy event_info string stays in the legacy path until M3 and belongs to M2b views).
D7 The 10-minute popup reminder is owned by the postmortem slice: M2b adds [incident_postmortem] reminder_minutes (default 10) and passes it; M2a's MeetingRequest.reminder_minutes is a required explicit field validated 0 < n <= 40320, no default in core (core holds no meeting policy; a key with no reader in M2a would be dead config). Adapter tests pass 10. Caveat for NC8 (OQ4): Calendar documents reminders as the authenticated user's only, so the popup reaches the bot user's calendar, not attendees.
D8 Attendee emails are stripped and de-duplicated case-insensitively in order (legacy collected twice, harmless). Logs never carry emails or event text, only meeting id, status, error_code, retry_after (no PII, no secrets).
D9 Unclassified statuses keep the Meet precedent: a 400 or other unmapped HttpError propagates as a bug, not data (outbound-clients.md decision 2); only 409 on create and 410 on get/delete are handled locally because they are documented, expected outcomes. classify_google_error is NOT edited (shared by every Google adapter).
D10 Free/busy: CalendarAvailability.busy_periods(emails, start, end) returns OperationResult[Mapping[str, AttendeeBusy]] with one entry per requested email (case-folded key); AttendeeBusy.busy is tuple[BusyInterval, ...] or None, where None means UNKNOWN (per-calendar errors, missing from the response, tooManyCalendarsRequested) and is never an empty tuple. The port carries no availability heuristic: M2b maps free/busy/unknown and does quorum. The adapter batches requests of at most 50 calendars (Calendar's documented cap; a vendor-fixed limit, so a module constant) in one to_thread call, merges results, and parses the response's UTC "Z" strings with datetime.fromisoformat (the legacy [:-1] slicing is not reused). A whole-request failure is a classified error result, never "all free".
D11 HolidayCalendar (postmortem/interfaces.py): async observed_federal_holidays(years: Collection[int]) -> OperationResult[frozenset[date]]. It takes years because M2b NC7 needs every year a search window crosses (legacy fetched the current year only). Failure is a classified result; fail-open vs fail-closed is M2b's policy (legacy swallowed to []). The adapter (postmortem/adapters/canada_holidays.py) makes one GET per year (api/v1/holidays?federal=true&year=Y), reads each holiday's observedDate with explicit shape checks (missing key or non-ISO date is PERMANENT_ERROR INVALID_RESPONSE, never a caught KeyError), uses the vendor's classifier, and receives its client factory by constructor so tests inject an httpx MockTransport client. No cache (M2b decides).
D12 integrations/canada_holidays/: __init__.py, settings.py, client.py only (vendor contract). settings: CanadaHolidaysSettings(ConfigurationSlice) toml_table_header ("canada_holidays",), base_url (https, default https://canada-holidays.ca/api/v1), timeout_seconds (gt 0, default 10.0, the legacy value), connect_retries (ge 0, default 2); NO tenant entry and no credentials; get_canada_holidays_settings() lru_cache; validated at boot by one line in host_configuration.py beside :238. client.py: build_canada_holidays_client(settings=None) -> httpx.AsyncClient (base_url, timeout, AsyncHTTPTransport(retries=connect_retries); no I/O at construction) and classify_canada_holidays_error following classify_opsgenie_error (401/403 UNAUTHORIZED, 404 NOT_FOUND, 429 transient with Retry-After seconds, 5xx transient, other status PERMANENT HTTP_ERROR, timeout, connect, JSONDecodeError INVALID_RESPONSE, unknown re-raised). httpx retry covers only connections that never opened; every call is a GET, so no replay protection is needed.
D13 base_url as a key conflicts with configuration.md:61 ("a value the vendor fixes, such as a single public API host, is not configuration"). The program ruling and the repo preference (tuning as typed settings with defaults) keep it; the new ADR line must reconcile it: the API is open source and may be self-hosted, tests point at a stub, and the key is a default, not a tenant entry (OQ2).
D14 In-memory fakes ship with the ports (M2b, M3 pins and M4b tests use them): InMemoryMeetingScheduler (records created/patched/deleted, honours idempotency_key replay, fail_with, per-operation failures, get reflects patches and deletes) and InMemoryCalendarAvailability (busy intervals per email, unknown set, fail_with) in core/adapters/in_memory.py; InMemoryHolidayCalendar in postmortem/adapters/in_memory.py. Each explicitly subclasses its Protocol and has an adapter-vs-fake parity suite like the VideoCall one.
