Updated 2026-09-24 (decisions/plugin-architecture.md): new features live in app/features/, generated by the package generator (TASK-114), declared by an entry point and enabled per environment (TASK-112). The feature imports only app/contracts/ and capabilities' api.py (here app/capabilities/approvals/api.py), and registers its strategies through the approvals capability's hookspecs. It never imports infrastructure/ or server/.

Aligns with decisions/approvals.md and decisions/feature-packages.md. New feature package app/features/ai_keys that manages AI gateway (LiteLLM) API-key issuance requests as an approval workflow, built on the generic ApprovalWorkflowService capability (capabilities/approvals). This is the n=3 consumer confirming the capability is genuinely domain-agnostic; its EffectHandler integrates with the internally managed LiteLLM AI gateway.

Desired end state:
1. app/features/ai_keys is a plugin-registerable feature (pyproject entry-point, lifespan/hookspec registration; no import-time side effects).
2. It provides only its ApprovalPolicy (who approves an AI key request, thresholds, SoD) and EffectHandler (provision/rotate/revoke the key via the LiteLLM gateway through a thin app/integrations client); no generic workflow machinery lives here.
3. The LiteLLM gateway is reached through a thin outbound integration client (integrations layer) behind the effect strategy, never called directly from route/business code.
4. Pydantic only at the I/O boundary; frozen dataclasses internally; route coverage includes success and error-mapping paths.

Depends on the approvals capability extraction. The task-planner agent must scope this to a single reviewable PR or decompose it.
