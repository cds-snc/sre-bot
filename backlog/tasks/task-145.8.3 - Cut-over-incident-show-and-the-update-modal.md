## 0. Scope in one paragraph
`/sre incident show` and the update modal move from legacy modules/incident into incident.response. `show` opens the information modal from the record (find_incident_for_conversation), with the five roles (core's read_incident_roles: record, else the report's Drive properties through the 145.8.5.1 bridge), the report and meet links through the owning adapters (the stored url as the hint), severity, status, the three times, and the security flag. Each field has an Update button that pushes a field modal; its submission writes the record first (IncidentStore.update_fields for severity, the three times and security_incident; response's change_status for status), then the followers (report text, list row and channel notice for status; channel notice for the others), each follower failure logged and told to the submitter while the rest continue, then refreshes the root modal from the fresh record. The Retro Link is dropped (human ruling 2026-11-10); security_incident becomes editable (parent AC #6). Deleted with their registrations and tests: information_display.py, information_update.py, update_incident_document_status (AC #4) and the dead code they leave (section 5). Not in scope: SEV0 (L9b adds it to both pickers), the policy-help answer of #1853 (declare's, TASK-145.7.9/145.7.10; excluded here), title editing, the central incident modal (DRAFT-11), deleting update_incident_field or the L5r guard (kept, section 8).

## 2. Decisions (all proposed; reasons in the OQs)
D1 Orchestration in response: new response/service/fields.py `update_fields` (find -> IncidentStore.update_fields -> channel notice if writable). Status does not go through it: the modal's status field calls change_status with the modal's own pinned notice (comment #2). service/status.py `_channel_stage` is made public as `channel_stage` (a 2-line rename so fields.py reuses it; the only mechanical edit, enabling work for the behaviour).
D2 Registration: new entrypoints/slack_show.py `register_show(registrar, scopes)` called from entrypoints/slack.py register (+2 lines): command `show` under sre.incident (route_hierarchical_command, integrations/slack/provider.py:762, matches a registered child before dispatching to the current node, as status, roles and close); block action `incident.response.update_field.open` (every Update button, value = field); view submission callback `incident.response.update_field`; the info view's callback `incident.response.show`. All modal-internal, so prefixed and with no legacy alias (no id of a posted message is involved, so no attach_rebuilt_listeners_first is needed; the rewired pin calls provider._attach_interaction_listeners() after registering, as the roles pin does). The legacy "show" dispatcher entry, handle_show and both bot.action/bot.view lines are deleted in the same PR (migration.md rule 4: never both).
D3 Views in new entrypoints/slack_show_views.py (pure builders, comms precedent slack_views.py): info view, field view (date+time pickers, or one static select). No text field (the Retro Link is gone). Every string from the incident_response catalogue; private_metadata is {channel_id, locale} on the info view and {channel_id, locale, field} on the field view, never the incident (legacy put the whole incident in it; Slack allows 3,000 characters, https://docs.slack.dev/reference/views/modal-views). The incident is read fresh at each press and at each submission (D5).
D4 Options: severity none, sev-1..sev-4 (values and order as pinned; SEV0 arrives with L9b); status the five IncidentStatus values; security yes/no (no third state, incident-management.md:40). A stored severity outside the options (a future SEV0) gets no initial_option rather than an invalid one.
D5 Press: the listener acks, reads the incident once (find_incident_for_conversation, then initial value), reads the user's timezone only for a time field, and pushes through the contract. Slack's trigger_id expires 3 seconds after delivery (https://docs.slack.dev/surfaces/modals), so the press does one store read and at most one users.info before the push (A3). A refusal or a timezone failure is told to the user privately (chat_postEphemeral to the channel, roles precedent) and no view is pushed.
D6 Submission: ack first (an empty ack closes only the submitted view, https://docs.slack.dev/surfaces/modals), then in one asyncio.run inside incident_scope: record write, then followers, in this order. Status: change_status(..., notice=modal wording): record, report status line, list row, channel notice. Other fields: update_fields: record, channel notice. The notice goes to the record's conversation only when it is writable (the archived-channel rule of D4 of TASK-145.8.4); a follower that failed or was skipped is told to the submitter privately (the status reply's lines, reused); the record is never rolled back. Then the root view is replaced from the incident the write returned (a fresh record, not the show-time snapshot) through reply.update_view(root_view_id); a failed refresh (the user closed the modal: views.update answers not_found, https://docs.slack.dev/reference/methods/views.update) is logged at warning without a traceback and never reported as a failed update (OQ9).
D7 Concurrency (constraint 4, outbound-clients.md 2026-11-17: recompute, not retry): the modal sends absolute values, so a lost guard is already answered inside the store by one re-read and recompute (store.py:628-653). Nothing in L6a retries. A second loss (INCIDENT_RECORD_CONFLICT) is told to the submitter ("changed while saving, open the modal again") and nothing else runs. A value another responder changed after the modal opened is overwritten by the submitter's choice (last writer wins, as legacy; no stale-display detection, which would be an addition; OQ6). The root view is refreshed from the returned record, so it shows what is stored.
D8 Locale (i18n.md Locale resolution, 2026-11-17 line): show is a command, so it answers in the invoker's locale (payload.user_locale, resolved by the provider at provider.py:1133). The modal flow carries that locale in private_metadata, exactly as the approved roles modal does: the pushed view, the refreshed view, the private lines and the channel notice use it. In en-US the notice is byte-identical to the pin; a payload with no readable locale in its metadata is answered in English then French. This reads the i18n line as "the payload names none" being false once the metadata names one; the line is clarified in the ADR with this PR (OQ3).
D9 (VOID, OQ5 approved): no timezone lookup. One datetimepicker per time field: initial_date_time = the stored epoch (omitted when unset), the submission stores the returned epoch (state key selected_date_time, verified against a recorded payload first). The notice renders the instant as <!date^{epoch}^{date_num} {time}|{UTC ISO}>. Was: D9 Timezone: the user's tz comes from users.info through the Bolt client the listener receives (legacy parity; the pin fakes users_info). The conversion uses zoneinfo, not pytz and not modules/incident/utils.py. An unreadable timezone refuses privately and writes nothing (legacy raised inside the listener). No contract for it now (OQ5).
D10 Links: IncidentReport.link(incident.report) and VideoCall.link(incident.video_call) (providers.video_call() added, ~5 lines, wrapping get_video_call); the stored url is the hint the adapters return. A reference with no link renders its label without a link, never "<None|...>".
D11 SlackReplySender gains `push_view(*, trigger_id, view) -> OperationResult[str]` (contract, provider, factories fake; the same classified path as open_view) so the listener never uses the raw Slack client for a view (reply.py docstring rule). Bolt's client is used only for users.info and the private ephemeral, as slack_roles.py does (OQ4).
