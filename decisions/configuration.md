# Configuration

## Context

Almost every setting is read from environment variables today, through about three dozen `BaseSettings` classes. The configuration files exist (`app/config/base.toml`, `local.toml`, `ci.toml`, `production.toml`), loaded by `server/configuration/` and read through the `ConfigurationSlice` base in `contracts/configuration.py`; the host slices (`[logging]`, `[server]`, `[slack_transport]`, `[scheduler]`), `[security]` and `[slack]` read them so far.

Current code:
- AWS settings live only in `integrations/aws/settings.py`, which reads `[aws]` (the client tuning) and the optional `[aws.tenant]` (the managed organisation: Identity Center instance id and ARN, and the role ARNs). The region and the dynamodb-local endpoint are the SDK's (`AWS_DEFAULT_REGION`, `AWS_ENDPOINT_URL_DYNAMODB`), declared by no field. The SSO permission sets are access policy and live in `packages/access/common/settings.py` (`[access_permission_sets]`). Slack settings live only in `integrations/slack/settings.py`, which reads `[slack]` and `[slack.tenant]` and its tokens as `SLACK__<FIELD>`. OpenAI reads `[openai]` and `[openai.tenant]` with its key as `OPENAI__API_KEY`; Notify and Opsgenie read `[notify]` and `[opsgenie]` (a timeout) and their `.tenant` API host, with their credentials as `NOTIFY__<FIELD>` and `OPSGENIE__INTEGRATIONS_KEY`; Trello's entry is its credentials, `TRELLO__TENANT__<FIELD>` (environment only), beside `TRELLO__ATIP_BOARD`; MaxMind reads `[maxmind.tenant]` `database_path`. Sentinel still reads flat names (TASK-171). Each lives only in `integrations/<vendor>/settings.py`, and Google in `integrations/google_workspace/settings.py`, which reads `[google_workspace]` and its whole tenant entry (customer id, service-account key, delegated user) as `GOOGLE_WORKSPACE__TENANT__<FIELD>`. `GOOGLE_RESOURCES`, the Google document and folder ids of several features, is read by `GoogleResourcesConfig` in the same module.
- Some feature settings sit with their feature (`packages/access/common`, `incident/scribe`, `oncall_sync`, `user_rotations`); others sit in `infrastructure/configuration/features/` (`atip`, `aws_ops`, `groups`, `incident`, `sre_ops`).
- Security settings (`issuers`, the `cors_allowed_*` lists and `dev_bypass_enabled` in `[security]`; `SECURITY__DEV_BYPASS_TOKEN` from the environment only) live in one `SecuritySettings` slice in `infrastructure/security/settings.py`, beside the code that reads them; TASK-116 moves both to `server/security/`.
- `AppSettings.environment` is typed `Literal["local", "ci", "production"]`, is required, and drives environment-conditional behaviour. The app runs in three places: local development (including GitHub Codespaces), the CI workflow, and one production deployment on ECS Fargate.
- Production values come from two SSM parameters, `sre-bot-config` and `sre-bot-config-infrastructure`, each a block of `KEY=value` lines mixing secrets and non-secrets, which `app/bin/entry.sh` writes to `.env` at container start. The task definition adds `BACKEND_URL`, `CORS_ALLOWED_ORIGINS`, `FORWARDED_ALLOW_IPS` and `SLACK__COMMAND_PREFIX` as plain environment variables and one secret (`GCP_SRE_SERVICE_ACCOUNT_KEY_FILE`) through `secrets:`. `AppSettings.PREFIX` no longer exists, and the `Settings` aggregator in `infrastructure/configuration/settings.py` is gone.
- Which features and jobs run is decided by environment variables and `ENVIRONMENT` checks in code.
- Vendor clients have no enablement rule, because they are clients, not plugins, and the per-entry-point key never reaches them. The Slack transport's switch is `[slack_transport] enabled`, apart from the Slack slice, so running the transport and having a Slack workspace are two facts (the interim `SLACK_ENABLED` mixed them until TASK-112.1). Google has no flag: it is in use when `GOOGLE_WORKSPACE__TENANT__CUSTOMER_ID` is set, which then needs its key, and the customer id is never blank or the `my_customer` API alias.

The app is promoted as one image through every environment, and plugins are enabled per environment ([plugin-architecture.md](plugin-architecture.md)). Environment variables are a poor home for non-secret, reviewable configuration: they are invisible in the repo and differ silently between environments.

## Decision

**Settings live with their owner.** Each owner defines one typed `pydantic_settings.BaseSettings` slice next to its code:
- features: `features/<feature>/settings.py`;
- capabilities: `capabilities/<capability>/settings.py`;
- hosting services: `infrastructure/<service>/settings.py`;
- vendor clients: `integrations/<vendor>/settings.py`.

A vendor slice holds the connection only: the endpoint, the credential and transport tuning (timeouts, retries). What a consumer asks the vendor for (a model, an output budget, a temperature) belongs to the consumer: a capability's defaults in its own slice, and a feature's values in the feature's slice, passed per call. Spring AI keeps the connection properties apart from the chat options, which are defaults a request overrides ([Spring AI OpenAI chat](https://docs.spring.io/spring-ai/reference/api/chat/openai-chat.html)).

A system reached in more than one role holds one least-privilege credential per role, not one shared login. For example, Slack's bot and Socket Mode tokens (transport) are separate from an admin token used by a feature that changes Slack ([platform-transports.md](platform-transports.md)). A recurring job's schedule and lease TTL belong to the job's feature, not a central scheduler slice ([reliability.md](reliability.md)). The security domain owns a `SecuritySettings` slice: issuers and JWKS, the CORS allow-list, the rate-limit backend and the dev-bypass settings. One key has exactly one owning slice.

**Values come from checked-in TOML configuration files.** `app/config/base.toml` holds defaults for every slice; one file per `ENVIRONMENT` value (`local.toml`, `ci.toml`, `production.toml`) overrides it. Files are reviewed like code and validated at boot. The base file is secure and production-shaped (dev bypass off, no wildcard CORS); `local.toml` holds the developer-friendly overrides and the values every development environment shares, the development Slack app's workspace id included; development secrets come from the repository's Codespaces secrets (`app/.env` off Codespaces) under the production `<SLICE>__<FIELD>` names. `ci.toml` configures no vendor tenant and switches off every plugin that requires a vendor (a test that needs one switches it on with fakes), and the test run blanks the vendor secrets so a Codespace's secrets never configure it.

**Loading order.** An identity slice reads `ENVIRONMENT` and `GIT_SHA` from the process environment only, never from a file, and selects the files: the base file, then the environment file. Both must exist; pydantic-settings silently skips a missing file, so the loader checks. The two files are deep-merged, so an environment file overrides key by key and never drops the base file's other keys in a table (`TomlConfigSettingsSource(..., deep_merge=True)`). Each slice reads only its own table (`toml_table_header`, pydantic-settings 2.15 or later: [releases](https://github.com/pydantic/pydantic-settings/releases)). A value resolves from, highest first: constructor arguments (tests), the process environment, the `.env` file, the configuration files, the field default. The settings-slice base class and the Protocol that supplies the file list are in `contracts/configuration.py`, so every layer that owns a slice can import them; the loader that implements the Protocol is host code in `server/configuration/` ([plugin-architecture.md](plugin-architecture.md)). This is the order ASP.NET Core and Backstage use: the host learns its environment first, then loads the base and environment files ([ASP.NET Core configuration](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/configuration/), [Backstage configuration](https://backstage.io/docs/conf/writing)). Loading runs once, in the app factory, before the app and its middleware are built ([lifecycle.md](lifecycle.md)).

**Host facts are a contract.** The identity slice and the host's own slice (`[server]`: the public base URL, the request body limit, the startup-message channel) are host code in `server/configuration/`. From them the host builds one frozen `HostInfo` (environment, git SHA, public base URL), defined in `contracts/configuration.py` and installed once at startup, as the loader installs the configuration files. Code outside `server/` never reads a host slice: new code receives `HostInfo` through its constructor or the service registry, and code not yet on the registry reads it through the contract's accessor. This is how ASP.NET Core hands services `IHostEnvironment` and Backstage hands plugins the backend's base URL through its discovery service ([ASP.NET Core environments](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/environments), [Backstage discovery service](https://backstage.io/docs/backend-system/core-services/discovery)). A feature that behaves differently per environment reads its own configuration value, set per environment file, never `HostInfo.environment`.

**Environment variables carry only secrets and platform-provided names.** The platform-provided names are a closed list: `ENVIRONMENT`, `GIT_SHA` and `FORWARDED_ALLOW_IPS` (derived from the VPC subnets by terraform and read by uvicorn, not the app: [uvicorn settings](https://uvicorn.dev/settings/)). Everything else, including values terraform could compute such as the public URL and the CORS origins, is in the configuration files, where a change is reviewed. Names that an SDK or runtime reads itself (`AWS_*`, including `AWS_REGION` and `AWS_ENDPOINT_URL_<SERVICE>` ([AWS SDK endpoints](https://docs.aws.amazon.com/sdkref/latest/guide/feature-ss-endpoints.html)), `UVICORN_*`, `OTEL_*`) are outside the app's naming rule: no slice declares them as fields, and the ownership check allow-lists them.

**Non-public values travel like secrets.** A value that is not a credential but whose publication in this public repository widens the impact of a mistake elsewhere is a non-public value: a Google Drive item id (a file or folder shared by link without a resource key opens to anyone who has its id, and ids are partly predictable: [Drive resource keys](https://developers.google.com/workspace/drive/api/guides/resource-keys)) the address of an account that holds domain privileges (the Google delegation subject), and an internal tenant identifier the vendor shows only to its administrators (the Google Workspace customer id: [Find your customer ID](https://support.google.com/a/answer/10070793); the AWS Identity Center identity store id and instance ARN, the first also the default access portal subdomain: [access portal URL](https://docs.aws.amazon.com/singlesignon/latest/userguide/howtochangeURL.html)). Such a value is never in a configuration file: its key is declared in `base.toml` with an empty default, so the table stays reviewable (or named in the table's comment when it belongs to an entry whose presence has a meaning, such as a vendor's tenant entry), and the value comes from the environment under the key's `<SLICE>__<FIELD>` name, through the same SSM SecureString parameter and `secrets:` entry as a secret (a Codespaces secret in development), which overrides the file key by the ordinary resolution order. It is not logged in full. An identifier that opens nothing on its own (a Slack workspace or channel id, a Google customer id) stays in the files: like an AWS account id, it is shared deliberately but is not secret ([AWS account identifiers](https://docs.aws.amazon.com/general/latest/gr/acct-identifiers.html)). Backstage draws the same line: configuration files are the default, and a value that must not be committed is substituted from the environment ([Backstage configuration](https://backstage.io/docs/conf/writing)). Values an organisation supplies as content rather than deployment configuration (document templates and their ids among the candidates) are TASK-167's.

**Environment names mirror the configuration path.** A secret a slice reads from the environment is named `<SLICE>__<FIELD>`: the slice's table name and the field, joined by a double underscore, with nested entries joined the same way (`<SLICE>__<ENTRY>__<FIELD>`). Each slice sets `env_prefix="<SLICE>__"` and `env_nested_delimiter="__"` and declares no per-field environment alias, which pydantic-settings applies without the prefix ([pydantic-settings](https://pydantic.dev/docs/validation/latest/concepts/pydantic_settings/)). The double underscore is the hierarchy separator of ASP.NET Core and Dynaconf ([ASP.NET Core configuration](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/configuration/), [Dynaconf](https://www.dynaconf.com/envvars/)); it cannot collide with platform and SDK names such as `AWS_REGION`, or with a field name that contains a single underscore. The platform-provided names keep their bare names.

**Case.** Field names and TOML keys are lower snake_case (PEP 8 attribute names, TOML convention); a key that is data rather than a field name, a plugin's entry-point name in `[plugins.<area>]`, is quoted lower snake_case segments joined by dots (`"incident.comms"`), which the loader accepts because it is still all lower case, and a dotted key in any other table fails that slice's `extra="forbid"`; environment names are upper case, the convention POSIX sets for environment variables ([POSIX XBD 8.1](https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap08.html)). Each slice sets `case_sensitive=False`, so `GOOGLE_WORKSPACE__TENANT__SERVICE_ACCOUNT_KEY` fills `tenant.service_account_key`, as Spring Boot's relaxed binding and ASP.NET Core's case-insensitive keys bridge the same gap ([Spring Boot external configuration](https://docs.spring.io/spring-boot/reference/features/external-config.html)). `case_sensitive=True` would force upper-case field names and TOML keys, and since pydantic-settings 2.15 it also applies to file sources and nested keys. Two names that differ only by case are one key for ownership, which the CI check compares case-insensitively.

**Renaming an environment name.** The new name is published on the deployment side beside the old one before the code that reads it deploys; the code reads only the new name, with no alias and no compatibility shim; the old name is removed once the deploy is verified. The ECS circuit breaker rolls a failed deploy back to the previous task-definition revision, which runs the previous image and still reads the old name, so rollback stays safe ([deployment.md](deployment.md)). A value is never renamed in place inside a store that both revisions read. This is a parallel change whose contract step follows the verified deploy ([Parallel change](https://martinfowler.com/bliki/ParallelChange.html)).

**Plugin enablement lives in the configuration files.** Every plugin's entry point has an enablement key in the base file; an environment file may override it. The host skips a disabled plugin before registering it and never validates its settings slice ([plugins.md](plugins.md)). The keys are grouped by product area ([product-scope.md](product-scope.md)): one `[plugins.<area>]` table per area maps each entry-point name to a boolean (`"incident.comms" = true`), the id-to-boolean shape Backstage uses to switch extensions ([configuring extensions](https://backstage.io/docs/frontend-system/building-apps/configuring-extensions)). The host reads the tables as maps and never names a plugin in code, so a new plugin is still one entry-point line and one key; boot fails naming the name when an installed entry point has no key, a key names no installed entry point, or a name sits under two areas. Host code that is not a plugin has its own run switch in its own table: the Slack transport (`[slack_transport] enabled`) and the scheduler (`[scheduler] enabled`, [reliability.md](reliability.md)); neither is ever an `ENVIRONMENT` comparison. A developer switches a plugin on for themselves from `app/.env` without editing a file, for example `PLUGINS__PLATFORM_ACCESS='{"access.sync": true}'`; the variable merges into the table key by key, and the boot rules still apply.

**Vendor enablement is the presence of a tenant entry.** A vendor client (`integrations/<vendor>/`) is available when its settings slice holds a tenant entry (`SubModel | None`, a list once an instance has several tenants), as Backstage enables an integration by configuring it ([Backstage integrations](https://backstage.io/docs/integrations/), [pydantic-settings nested models](https://pydantic.dev/docs/validation/latest/concepts/pydantic_settings/)). There is no `<VENDOR>_ENABLED` key. A present entry requires its secrets and is shape-checked at boot with no network call; an absent entry means the vendor is not configured. An invalid vendor slice fails boot, like a capability slice. A vendor slice never makes its own tenant entry required: whether a vendor is required is its consumers' decision, and an enabled plugin whose required vendor is not configured aborts boot ([plugins.md](plugins.md)). Every vendor slice has this one shape, so adding, removing or switching a vendor is a configuration change. The entry holds what this deployment needs to reach its tenant and act in it: the vendor's tenant id where it has one ([workplace-systems.md](workplace-systems.md) rule 3), an endpoint or location only where the deployment chooses one (a regional or self-hosted API host, a model gateway, a local database file), and the credentials. A value the vendor or its SDK fixes, such as a single public API host, is not configuration: Backstage's integration entries carry a host because GitHub, GitLab and Bitbucket can be self-hosted ([Backstage GitHub integration](https://backstage.io/docs/integrations/github/locations)), while a single-host SaaS plugin has no endpoint key. Where only the credentials identify the tenant, the credentials are the entry, read from the environment as `<VENDOR>__TENANT__<FIELD>`, as Google's and AWS's entries are environment-only (PagerDuty's Backstage backend plugin configures a block holding only its API token: [PagerDuty Backstage integration](https://support.pagerduty.com/main/docs/backstage-integration-guide)). Where an entry holds non-secret values, the credentials stay fields of the slice (Slack, OpenAI, Notify, Opsgenie). Runtime on/off is a flag, not vendor setup ([OpenFeature](https://openfeature.dev/docs/reference/intro)). A platform transport is host code, not a vendor client: it has an enablement key in the configuration files like a plugin ([plugins.md](plugins.md)).

**A transport's settings are not its vendor's.** A platform transport owns its own table, `[<platform>_transport]`, beside the vendor client's table: `[slack_transport]` holds `enabled`, `socket_mode` and `command_prefix`, and `[slack]` holds the Slack client's credentials and tenant entry. The transport reads the vendor's credentials; it never declares them. Spring Boot binds one prefix per configuration class and Backstage keeps `integrations` apart from the plugins that use them, for the same reason: one key, one owner ([Spring Boot external configuration](https://docs.spring.io/spring-boot/reference/features/external-config.html), [Backstage integrations](https://backstage.io/docs/integrations/)).

**Slack credentials follow Slack's token model.** The bot and user tokens belong to one workspace installation and the app-level token to the app ([Slack tokens](https://docs.slack.dev/authentication/tokens)). The app runs in one workspace, so the tokens and the signing secret are fields of the Slack slice itself (`SLACK__BOT_TOKEN`, `SLACK__USER_TOKEN`, `SLACK__APP_TOKEN`, `SLACK__SIGNING_SECRET`), as a single-workspace Bolt app is configured, and `[slack.tenant]` holds the workspace's ids. A present tenant entry requires the bot token, and a Slack token set without a tenant entry fails boot naming the key, so Slack is never half configured. An app installed in several workspaces keeps per-installation tokens in Bolt's OAuth installation store, not in configuration ([Bolt OAuth](https://docs.slack.dev/tools/bolt-python/concepts/authenticating-oauth)); that is a new decision, not a list of tenant entries. Google's service-account key is per tenant and is named `GOOGLE_WORKSPACE__TENANT__SERVICE_ACCOUNT_KEY`; the delegation subject the key acts as, a non-public value, is `GOOGLE_WORKSPACE__TENANT__DELEGATED_USER_EMAIL`. Which principal each Google caller uses, the minimum scopes and keyless authentication are TASK-169's.

**Runtime flags use OpenFeature.** Gradual rollout or a kill switch without a deploy uses [OpenFeature](https://openfeature.dev/) with the self-hosted flagd provider, added only when a feature needs one. Configuration files are not reloaded at runtime.

**Environment identity.** `ENVIRONMENT: Literal["local", "ci", "production"]`, required with no default, is the only source of "which deployment am I?". `local` is development on a workstation or in Codespaces, `ci` is the test run (locally and in the CI workflow), `production` is the deployment. Adding an environment is one more `Literal` value and one more configuration file; a test fails when a value has no file. Deriving it from hostnames, prefixes or `sys.modules` is prohibited. Security-relevant toggles (dev bypass) also need their own explicit boolean that defaults off: two independent guards. Command naming, so a dev and a prod bot coexist in one Slack workspace, is a transport setting (`command_prefix` in `[slack_transport]`) and is never derived from `ENVIRONMENT` ([transport-slack.md](transport-slack.md)).

**Fail fast, on static checks only.** Every slice validates in lifespan's configuration phase ([lifecycle.md](lifecycle.md)); an invalid file or a missing required secret fails boot with a message naming the key. Every slice on the configuration files sets `extra="forbid"`, so a misspelled key in its table fails boot naming it; a table that no slice owns fails the CI check. A setting a feature needs only when it is enabled is required by that feature's slice, which is validated only when the plugin is enabled. An invalid slice fails boot in every layer ([plugins.md](plugins.md)). Validation checks presence and shape and never calls a service. Whether a credential actually works is the plugin's credential check, run after registration ([lifecycle.md](lifecycle.md)). `access/request`'s `ACCESS_REQUESTS_FALLBACK_APPROVER_SLUG` validator is the pattern.

**Secrets.** Secret material resolves through the secrets contract ([cloud-portability.md](cloud-portability.md)) or is injected by the platform at deploy time. On ECS each secret is one SSM SecureString parameter, `/sre-bot/<SLICE>__<FIELD>`, injected under its `<SLICE>__<FIELD>` name by the task definition's `secrets:` ([ECS secrets from Parameter Store](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/secrets-envvar-ssm-paramstore.html)). Terraform creates each parameter with a placeholder through the write-only `value_wo` argument (Terraform 1.11 or later) and adds its `secrets:` entry; the value is set outside terraform, so it never reaches terraform state or the repository. `ignore_changes` on `value` would not do this: every refresh reads the decrypted value into state ([aws_ssm_parameter](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/ssm_parameter)). A secret missing at start keeps the task from running, and the circuit breaker rolls back. One parameter per secret matches the existing service-account key parameter, costs nothing at the standard tier, and lets each value change alone; Secrets Manager's rotation does not apply to these vendor tokens. No container-start script fetches configuration. Plain environment-variable secrets are tolerated, not the target. Secrets never appear in configuration files, defaults, logs ([observability.md](observability.md)) or `repr`. JWKS refreshes at runtime; static secrets rotate by redeploy.

**Consumers receive slices.** A service constructor takes its own settings slice, nothing wider. No aggregator of all settings exists.

**Migration rides with the work.** Any task that touches a domain's service moves that domain's slice to its target home in the same change and deletes the old one. That covers slices whose move is scheduled. Slices with no scheduled move (the host, security, vendor and hosting slices), and every value production sets today, move onto the configuration files in TASK-111, so no value is left in the old store. A feature value moves under its current class's table: table names do not depend on module paths, so a later package move relocates the class and leaves the files alone.

## Consequences

- "Where is this configured?" has one answer per owner; deleting a feature deletes its configuration.
- Differences between environments are visible in a diff of two files.
- A typo in `ENVIRONMENT` or a configuration key is a validation error at boot.
- Cost: a change to non-secret configuration needs a PR and a deploy; runtime changes need a flag.
- `production.toml` holds this organisation's deployment values in the app repository for now. Public or not, they are the deploying organisation's, not the framework's: they move, every slice at once, to the organisation's deployment repository when it exists ([product-scope.md](product-scope.md)), leaving `base.toml`, `ci.toml` and an example `local.toml` here. Until then an organisation-specific value is not moved to the secret pipe for that reason alone; the non-public rule decides that.

## Checks

- CI (`bin/check_settings_key_ownership.py`): each key is owned by exactly one settings slice, compared case-insensitively.
- Secrets in the repository: GitHub secret scanning, and the developer's own care; no second scanner or secret-shaped key rule in CI.
- Review: no non-public value (a Drive item id, a domain-privileged account's address) in a configuration file; its key is in `base.toml` with an empty default, or named in a comment there when it belongs to a tenant entry.
- CI (same script): each table in a configuration file is named by exactly one slice's `toml_table_header`, and every table a slice names is in `base.toml`.
- CI (same script): a slice on the configuration files reads only `<TABLE>__` names or a platform-provided name, and never a name in the SDK and runtime namespaces; slices still on flat names are held to this once they move onto the files.
- Unit test: `base.toml` and one file per `ENVIRONMENT` value exist and parse.
- Boot test: a missing configuration file, malformed TOML or an unknown key in a slice's table fails boot naming the file, table and key.
- Boot test: every plugin entry point has an enablement key in the base file.
- Boot test: a disabled plugin's slice is never validated; an enabled feature with a missing required key aborts boot with an event naming the key; an enabled plugin whose required vendor has no tenant entry aborts boot naming the key.
- Boot test: missing required secret → clean failure naming it.
- Boot test: a vendor slice with a tenant entry missing a secret or failing its shape check fails boot naming the key; an absent entry boots with the vendor unconfigured and no network call.
- CI (same script): no settings key named `<VENDOR>_ENABLED` in `integrations/`, with no exception; no `os.environ` or `os.getenv` reads outside settings classes (`bin/` developer scripts and tests excepted).
- grep: no environment derivation outside `ENVIRONMENT`.
- Review: no feature or capability reads an environment variable directly.
