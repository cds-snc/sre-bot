# Internationalization

## Context

English and French are peers: an Official Languages obligation, not a nice-to-have.

Current state: two systems coexist.
- Legacy modules (`atip`, `incident`, `role`, `secret`) use `python-i18n` against central `app/locales/*.yml`.
- New features use the in-house `app/infrastructure/i18n/` stack (`TranslationService`, `Translator`, YAML catalogues per feature under `locales/`), registered through the `register_i18n_resources` hookspec.
- EN/FR parity is tested only per feature (e.g. `incident_draft`, `incident_summary` locale tests); no CI check covers every registered catalogue.

## Decision

**i18n is a framework service** ([plugin-architecture.md](plugin-architecture.md)). The translator contract lives in `app/contracts/`; its implementation is host code in `app/server/`. Features and capabilities depend only on the contract.

**Every user-facing string goes through the translator contract.** No user-facing literal is built in a handler, renderer or service without a catalogue key.

**The implementation uses a maintained library,** chosen in a separate decision. The in-house stack is tolerated until then; the contract is shaped so that swap changes no feature.

**Catalogues stay in the feature.** Each feature owns its `locales/` directory and registers it at startup through a hookspec in `contracts/`, so translations live in the vertical slice.

**The bilingualism guarantee is a CI gate, not a runtime fallback.** Every user-facing key must exist in both `en` and `fr` catalogues; the parity check fails the build otherwise. Runtime fallback to the default locale exists only as a safety net for deploy-time races; it is not the compliance mechanism.

**Locale resolution** is per request, from the platform signal (Slack payload locale, `Accept-Language`), bound to `contextvars` at the inbound boundary alongside correlation. Services and renderers read it from context; passing `locale` explicitly is fine in pure helpers. Pick one per function; don't thread both.

**Slack help and commands** are localized via `description_key`/`example_keys` referencing catalogue keys; plain `description`/`examples` literals are deprecated once parity covers the registered commands ([transport-slack.md](transport-slack.md)).

## Consequences

- Features see one contract, so replacing the in-house stack with a library is a host change only.
- The parity gate is the point: missing French becomes a build failure, not a production surprise.
- Cost: until the library decision lands, the in-house stack owns plural rules and formatting edge cases.

## Checks

- CI parity check across every registered catalogue (en ↔ fr key sets equal).
- New feature PRs with user-facing text include both catalogues.
- import-linter: features and capabilities import the translator only from `contracts/`.
- grep (after migration): no `import i18n` (python-i18n) anywhere in `app/`.

- the in-house implementation in `infrastructure/i18n/`, imported directly by features;
- `register_i18n_resources` in `infrastructure/plugins/specs.py` instead of `contracts/`.
