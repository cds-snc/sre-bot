# API Security

## Context

The 2026-07 review found production CORS resolving to wildcard-with-credentials, an in-memory rate limiter bypassable via a client-set header, JWT validation skipping audience/issuer checks, and bearer-URL-only webhooks. This record states the binding rules; the hotfix ticket closes the gaps. Slack inbound verification is owned by [transport-slack.md](transport-slack.md).

## Decision

**Authentication (HTTP):** JWT bearer tokens validated against configured issuers via JWKS. Non-negotiable per token: signature (algorithms pinned to the asymmetric set configured per issuer — never `HS*`, never token-driven), `exp` (required present and valid), `nbf` (validated whenever present — it is optional in RFC 7519 and many issuers omit it), `iss` (passed to `decode`, matched against the issuer whose keys verified the token), and `aud` (required in every issuer config; a config without an audience fails boot). The issuers are `[[security.issuers]]` entries in the configuration files, each validated at boot: only `issuer`, `jwks_uri`, `algorithms` and `audience`; `jwks_uri` over https (http only on a loopback host, for the local token server), as OpenID Connect Discovery requires of a key set URL; `algorithms` a non-empty subset of the asymmetric set, `RS256` when absent ([RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html) 3.1); one entry per issuer. A bad entry is a defect in a reviewed file and fails boot naming the issuer and key ([lifecycle.md](lifecycle.md)). JWKS refreshes at runtime with fail-degraded semantics (an unreachable key set → that issuer's tokens 401, app still serves).

**Identity:** one frozen `User` value type per request. For Backstage JWTs, `sub` identifies the token's subject and email is a display and correlation attribute, never the key. The entry point resolves the caller to a person ([people-and-accounts.md](people-and-accounts.md)). Token scopes (`scope`/`scp`) only say that the caller may use the bot API. Feature permissions come from the bot's own policy ([authorization.md](authorization.md)), the same for every entry point. Routes are authenticated by default, and an unauthenticated route is an explicit, commented decision. Object-level authorization (who may act on *this* resource) is the service layer's job, and every feature PR states its answer.

**Dev bypass:** requires `ENVIRONMENT != "production"` **and** `dev_bypass_enabled = true` (default false, set by a developer as `SECURITY__DEV_BYPASS_ENABLED`) — two independent guards ([configuration.md](configuration.md)); every use is logged. No checked-in file turns it on. In production, the flag on or a `SECURITY__DEV_BYPASS_TOKEN` present fails boot naming the setting: a debug feature is disabled in production ([OWASP ASVS 5.0](https://github.com/OWASP/ASVS) V13.4.2), and a reviewed-config defect stops the deploy rather than running behind the request guard ([lifecycle.md](lifecycle.md)). Spring Boot disables DevTools in packaged applications for the same reason ([Spring Boot DevTools](https://docs.spring.io/spring-boot/reference/using/devtools.html)).

**CORS:** explicit origin allow-list from the security settings slice, empty by default. A validator rejects `*` in the origin, method and header lists at boot, in every environment. No credentials mode: the API authenticates with bearer tokens in the `Authorization` header, which needs none, so an allowed origin cannot ride a user's cookies. Allowed methods default to the ones the API serves (`GET`, `POST`). No environment-derived origin logic.

**Rate limiting:** SlowAPI with a shared storage backend (`redis://`) whenever more than one replica can run; `memory://` only for local. Keyed per-principal when authenticated, per-IP otherwise. **No header-based exemptions** — trusted internal sources authenticate like everyone else. 429s are problem-details with `Retry-After` ([errors-and-http.md](errors-and-http.md)). Default limits apply to all routes; exemptions (health) are explicit.

**Headers:** one middleware sets, on every response: `Strict-Transport-Security` (max-age ≥ 1 year, `includeSubDomains`), `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'` (the anti-embedding control — ASVS 5.0 treats `X-Frame-Options` as obsolete; include it only as a legacy extra), `Referrer-Policy`, and a restrictive `Permissions-Policy`.

**Webhooks (amended 2026-07-24):** the SRE Bot is the organization's single webhook ingress — teams do not stand up their own apps — so inbound authenticity follows a **tiered trust model** rather than one blanket rule. *Provider-signed* (e.g. AWS SNS): the provider signature is verified in **all** environments, never environment-gated. *Shared-secret HMAC* (issuer-provisioned): the target state for every Bot-issued webhook — a per-webhook secret, HMAC over the body, constant-time compared. *Hardened secret-URL* (legacy / arbitrary sender): a high-entropy `webhook_id` path with the body treated as fully untrusted — a **time-boxed, tracked exception**, never a resting state, retained only until observability migrates each live sender to a signed tier. Because the Bot is the sole issuer, new webhooks are **secure-by-default**: a secret is minted at creation and HMAC is enforced from day one. The legacy unsigned population is retired observability-first — every request is fingerprinted (source IP, user-agent, matched payload type, signature-header presence) to build the known-sender inventory, then moved to a signed tier under monitor-then-enforce rollout. Unauthenticated acceptance of a not-yet-migrated legacy webhook is **risk-accepted in writing** (m-0 exit), never silent. Across all tiers, controls bind regardless of auth state: bodies have a size cap; every webhook instance is independently revocable; rate limits are keyed per instance (`instance_ref`, below); and **payloads are data, never trusted identity** — actor attribution and target selection (channel, action) come from the Bot's own webhook record, never the request body. CORS is a browser control and offers no protection for these server-to-server calls; webhook authenticity is governed solely by this clause.

**Webhook tiers in detail (amended 2026-11-25, TASK-168).** [webhooks.md](webhooks.md) applies these at its ingress.
- *AWS SNS*: every message type is verified; SignatureVersion 1 and 2 are both accepted, the version logged, and 2 preferred for topics the organisation owns ([verifying SNS signatures](https://docs.aws.amazon.com/sns/latest/dg/sns-verify-signature-of-message.html), [SHA256 signing](https://aws.amazon.com/blogs/security/sign-amazon-sns-messages-with-sha256-hashing-for-http-subscriptions/)). The signing certificate is fetched over https from an SNS host only. A bad signature answers **403** with a generic body that never says why, in every environment. An instance may carry a `topic_arns` allowlist, enforced once backfilled; a message from another topic is refused. A subscription is confirmed only when `SubscribeURL` is https on `sns.<region>.amazonaws.com`, with no redirects and a timeout setting, from the processor, never in the request ([OWASP SSRF](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)).
- *HMAC tier*: [Standard Webhooks](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md) v1 (HMAC-SHA256 over `id.timestamp.body`, `whsec_` secrets, a space-separated signature list), with a timestamp tolerance setting (default 300 s) and two active secrets during rotation; the old secret is kept until a configurable expiry, as Stripe overlaps rotations ([Stripe webhooks](https://docs.stripe.com/webhooks)). Other schemes in the signature list are ignored, so a sender cannot downgrade. A bad signature answers 403 (HMAC has no `WWW-Authenticate` scheme); 401 stays for bearer-token API routes. RFC 9421 and `v2a` (ed25519) are not adopted now.
- *Secrets at rest*: a webhook secret is encrypted at the application level with KMS, encryption context `{instance_ref}`, decrypted on verify and cached within a TTL setting; storage encryption alone does not stop a reader of the table, a backup, a restore or an export. A secret is shown once at creation, never logged, and **never exported**; an import mints new ones ("treat webhook secrets like database credentials", [OWASP Webhook Security](https://cheatsheetseries.owasp.org/cheatsheets/Webhook_Security_Cheat_Sheet.html)).
- *Identity is not the credential*: each instance has an internal, non-secret `instance_ref`. Logs, metrics, rate-limit keys, flag contexts, idempotency keys and chat button values use it; the URL `webhook_id` appears only in the route lookup. The URL is a durable public address for signed tiers and a revocable secret for the legacy tier.
- *Rate limit, two layers*: before the instance lookup, a per-address limit counts only unknown or inactive ids and failed verifications, with a short negative cache for unknown ids, so a spray of random ids costs no store read each ([OWASP API4:2023](https://owasp.org/API-Security/editions/2023/en/0xa4-unrestricted-resource-consumption/)); after it, the per-instance limit with an override. A per-address limit on known instances is wrong because all SNS traffic shares AWS address ranges.
- *Output encoding*: every value derived from a payload is escaped for the target format before trusted tokens (mentions, links the adapter builds) are inserted; for Slack, `&`, `<` and `>` ([Slack formatting](https://docs.slack.dev/messaging/formatting-message-text)). Templates render plain text.
- *Passthrough rule*: a payload never supplies interaction ids, impersonation fields or thread targets. Sender-built chat content (the legacy Slack-shaped protocol) loses `callback_id`, `action_id` and `block_id` values any feature registered, interactive elements without a `url`, `parse` and `link_names`, and `username`, `icon_*`, `thread_ts` and `reply_broadcast` unless the instance allows them, and gains a "via webhook" context line; monitored then enforced.
- *Hygiene*: POST only; an unexpected `Content-Type` is refused; the raw body is verified before parsing; `Authorization` and signature headers and bodies are never logged; alerts fire on signature-failure spikes, unknown-id sprays and sustained 4xx or 5xx.

**Machine callers.** Inbound callers fall into three classes ([webhooks.md](webhooks.md)): (1) first-party workloads that hold an identity call the owning feature's authenticated API under `/api/v1/`; (2) third parties and AWS services that can only sign use the webhook ingress with a provider signature or the HMAC tier; (3) legacy secret-URL senders are burned down. Which workload issuers are trusted for class 1, the audience and the claim-to-principal mapping are decided by TASK-194 in its own record.

**Request limits (amended 2026-11-20):** body size capped at the server; no unbounded `Body(...)` on public routes. A cap bounds bytes, not work: handling an untrusted body takes time linear in its size. A pattern applied to untrusted text has no overlapping repeats (adjacent or nested quantifiers that can split the same characters two ways); use possessive quantifiers or atomic groups where a repeat must not give back ([Python `re`](https://docs.python.org/3/library/re.html), 3.11+). A backtracking match holds the GIL, so one request stalls the whole process, not one worker. Each such pattern has an adversarial test at the body cap. CodeQL's `py/redos` and `py/polynomial-redos` are a backstop, not the check: they do not trace a payload through model parsing (no alert was raised on the two quadratic webhook patterns TASK-190 fixed). Sources, read on 2026-11-20: [CWE-1333](https://cwe.mitre.org/data/definitions/1333.html) (avoid backtracking or bound the input), OWASP ASVS 5.0 (Level 3: regular expressions free of exponential backtracking), CodeQL query help for [`py/polynomial-redos`](https://codeql.github.com/codeql-query-help/python/py-polynomial-redos/) and [`py/redos`](https://codeql.github.com/codeql-query-help/python/py-redos/) ("modify the regular expression to remove the ambiguity").

**Edge (amended 2026-11-03):** the WAF's `AuthorizedEndpoints` rule is a positive allow-list kept in step with the application's route table: every route the app mounts is reachable at the edge, and the allow-list exists only to drop requests for paths nothing serves (scanners, fuzzing, forgotten or framework-default paths). It never hides a served route: the code and its OpenAPI documents are public, so the docs routes are allowed, and access control stays the application's authentication and authorization. The list lives in one file, `terraform/authorized_endpoints.json`, read by terraform and by a CI test that loads every installed plugin's routes onto the app and fails on a mounted route the edge would block, on an entry that matches no route, and on a route under the authenticated `/api/v1/` prefix without `get_current_user` that is not recorded as public by decision. A route blocked at the edge on purpose is listed in that test with its reason; the list starts empty. The versioned API is one `/api/v1/` prefix entry, so a new route family needs no terraform change. Keeping the exposed surface equal to the documented one is what [OWASP API9:2023 Improper Inventory Management](https://owasp.org/API-Security/editions/2023/en/0xa9-improper-inventory-management/) asks.

## Consequences

- The trust model is uniform: verify at the boundary (transport or route), then code downstream assumes an authenticated principal.
- Redis becomes a deployment dependency for multi-replica environments — accepted; a broken limiter is worse.

## Checks

- Tests: JWT missing-`aud` config fails boot; tampered/HS256 tokens rejected; CORS validator rejects wildcards and the middleware sends no `Access-Control-Allow-Credentials`; unauthenticated request to a feature route → 401; provider-signed webhook with an invalid signature → 403 in all environments; a Bot-issued HMAC webhook with a missing/invalid signature → 403; an SNS message with SignatureVersion 1 or 2 verifies, one from a topic outside the instance's allowlist is refused, and a `SubscribeURL` off an SNS host is never fetched; an exported webhook instance holds no secret; payload text carrying `<!channel>` or `<@U123>` renders inert; oversized webhook body rejected; a not-yet-migrated legacy webhook is accepted only while flagged legacy and each acceptance emits an origin-fingerprint event; 429 carries `Retry-After`; each pattern over untrusted text handles an adversarial input at the body cap well under one second.
- Edge: the route-table test (`app/tests/unit/server/test_server_edge_allow_list_routes.py`) passes; `bin/deploy-checks.zsh post edge` shows the app, not the WAF, answering an `/api/v1` path after an allow-list change.
- grep: no `X-Sentinel-Source` (or any header-presence) limiter exemption; `allow_origins` never computed from environment shape.

## Migration

Ticket: Phase-0 security hotfixes — known gaps at adoption time: prod CORS wildcard+credentials, header-based limiter exemption, in-memory limiter across replicas, JWT `aud`/`iss` not enforced, generic webhook authenticity, SNS verification skipped outside prod. Generic webhooks were originally slated for mandatory HMAC in Phase 0; per the amended Webhooks clause this is now an observability-first, tiered migration — SNS-everywhere verification, exception-leakage removal, and the body-size cap land in Phase 0, while HMAC enforcement and secure-by-default issuance move to Phase 4, with the legacy unsigned population risk-accepted in writing until each sender is migrated. Nothing here is a tolerated divergence for new code: every newly issued webhook is signed from day one.

**Changes:**
- 2026-09-25: feature permissions come from authorization.md, not JWT scopes; token scopes grant API access only.
- 2026-10-20: CORS drops credentials mode (bearer tokens need none), methods default to `GET` and `POST`, and the settings live in the `SecuritySettings` slice (TASK-24.2).
- 2026-10-23: issuers move to `[[security.issuers]]` in the configuration files and each entry is boot-validated (https or loopback `jwks_uri`, asymmetric algorithms, audience, one per issuer); production refuses to boot with the dev bypass flag on or its token set; fail-degraded covers JWKS reachability only (TASK-111.8).
- 2026-10-29: the dev bypass enabled outside production and an empty issuer list log one `security_setting_weakened` WARNING naming the setting ([configuration.md](configuration.md), TASK-156 planning).
- 2026-11-03: the edge allow-list follows the route table: one JSON source read by terraform and a CI test, every mounted route reachable (OpenAPI docs included), `/api/v1/` opened as one prefix with authentication enforced by the test, six legacy entries with no route removed (TASK-163).
- 2026-11-20: request limits bound work as well as bytes: body handling is linear in its size, patterns over untrusted text have no overlapping repeats and an adversarial test at the cap, CodeQL is a backstop (TASK-190).
- 2026-11-25: webhook tiers in detail (TASK-168, lands with TASK-37.1): SNS SignatureVersion 1 and 2, 403 on a bad signature, a per-instance TopicArn allowlist, the `SubscribeURL` host rule; Standard Webhooks v1 as the HMAC tier with rotation; secrets encrypted with KMS at the application level and never exported; `instance_ref` separates identity from the URL credential; a two-layer rate limit; output encoding and the passthrough rule; a Machine callers pointer to TASK-194. A bad HMAC signature answers 403, not 401.
