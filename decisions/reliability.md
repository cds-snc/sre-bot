# Reliability

## Context

Slack redelivers, queues redeliver, retries retry, and multiple replicas race. **Nothing in this system provides exactly-once delivery** — not SQS FIFO, not DynamoDB Streams, not locks. Every durable guarantee therefore reduces to one primitive: idempotent consumers. The current idempotency store is a read-then-write cache with a TOCTOU race — the opposite of what four other decisions assume — which makes this the highest-priority correctness fix in the codebase.

## Decision

**Three primitives, not interchangeable backends.** Coordination reduces to three distinct primitives routinely — and wrongly — treated as substitutes: an **atomic conditional write** (compare-and-set on a linearizable store; DynamoDB today, ports to Redis `SET NX`, Postgres unique-insert, Cosmos conditional), a **durable queue** (at-least-once work handoff; SQS today), and a **change feed / CDC** (ordered mutation stream; DynamoDB Streams). Only the conditional write provides mutual exclusion and dedup — a queue cannot (SQS FIFO dedup is a 5-minute send-side window, not a durable claim) and a change feed only relays already-committed writes. Dedup, Tier-2 leases, and outbox claims are all uses of the **one** conditional-write primitive; the queue and the relay sit *beside* it, never replace it, and running multiple replicas is an argument *for* the conditional write, not against it. All three are hosting contracts: Protocols in `contracts/` (queue, coordination) implemented in `infrastructure/`, which plugins get from the service registry ([plugin-architecture.md](plugin-architecture.md)). The conditional write is the coordination contract; `idempotency` is only its first *use* — its Protocol is `ConditionalWriteStore` in `contracts/coordination/`, implemented in `infrastructure/coordination/`. Callers use it through two thin facades in `contracts/coordination/`: `LeaseStore` (`acquire`, `release`) and `IdempotencyStore` (`claim`, `complete`, `release`). Each facade is built with a required read-failure policy. The primitive carries no policy: when the consistent re-read after a contended claim fails, it reports `ClaimResult.INDETERMINATE` with no claim token, and the facade decides. Both facades are `FAIL_CLOSED` today (a lease is not acquired; a dedup claim is `IN_PROGRESS`). The policy is per use because a failed re-read is tolerable for a lease over idempotent job bodies, but failing open for dedup could re-execute an operation that already completed; TASK-100 flips only the lease.

**Idempotency.** Every mutating handler (Slack action, webhook, queue consumer, Tier-2 job) is idempotent via an **atomic conditional claim** on the durable store (the Powertools-idempotency pattern): key `<feature>:<intent>:<idempotency_id>`, claimed with DynamoDB `ConditionExpression: attribute_not_exists(pk)` and status `IN_PROGRESS` with a bounded in-progress TTL; updated to `COMPLETED` with the outcome on success; deleted on failure so redelivery retries. Both the update and the delete are conditional on the claim token (ownership rule below). A conditional-check failure branches: `COMPLETED` → return the recorded outcome; `IN_PROGRESS` unexpired → concurrent duplicate, reject/defer; `IN_PROGRESS` expired → the claimant crashed, take over and re-execute; `IN_PROGRESS` bearing the caller's **own claim token** → the caller's own write, replayed by its client's retry after a lost response — not a competitor, so it resolves to `NEW`. That fourth branch requires each claim to carry an opaque per-call owner token (portable: a DynamoDB attribute, a Redis `SET NX` value, a Postgres owner column); without it an ambiguous retry strands the key as `IN_PROGRESS` until its TTL expires, which matters for leases and is immaterial to dedup, where a replay and a genuine duplicate are the same event. The `idempotency_id` is a **sender-assigned identifier stable across redeliveries** — Slack `event_id`, the webhook provider's delivery id, the id embedded in the queue message or outbox event — **never** the middleware-generated `request_id`, which changes on every redelivered HTTP request. No payload hashes in keys, no truncation, no get-then-set. Where the domain entity lives in the same store, marker and entity go in one `TransactWriteItems`.

**Ownership on complete and release.** A `NEW` claim returns its claim token through the contract, and `complete` and `release` take it back: they apply only while that token holds the key, and otherwise change nothing and report that ownership was lost (a `False` result, not an error). `release` also never deletes a `COMPLETED` record. This closes one hazard: a claimant whose in-progress TTL elapsed and whose claim was taken over cannot delete or overwrite the new holder's record, so the lease is not freed while a run is still in flight. The limits are deliberate. It is **not fencing** — the protected resources (Slack, Google Workspace, AWS Identity Center) do not check tokens, so a stale holder can still act on them, and two runs can still overlap after a takeover; duplicate execution stays tolerated and is absorbed by idempotent bodies, never prevented by this rule. A record already purged by the TTL sweeper makes a late `complete` or `release` a no-op, and a client-retried `release` whose first attempt landed reports lost ownership although the release happened. The token is an opaque owner value on every backend (Redis compare-and-delete, a Postgres owner column, a Cosmos owner field or etag).

**Idempotency is not a general job-status store.** Dedup of a redelivered attempt (the claim/complete/release primitive above) and concurrency locking (a Tier-2 lease, same primitive) are both instances of the one conditional-write contract. Querying the current state of a long-running job for a poller (e.g. `GET /sync-runs/{job_id}`) is a **different capability** — a plain keyed record store that is read many times and overwritten as state progresses — and must not be modeled as a `get`/`set` cache smuggled in under the idempotency name; give it its own small Protocol even if it happens to share a table with idempotency records.

**Queuing.** Work that must survive a crash goes on the durable queue behind a capability Protocol (`QueueService`; SQS today). Semantics assumed everywhere: **at-least-once, possibly out of order.** Messages are control-plane signals — small, carrying `correlation_id` and intent; consumers re-fetch current state from the store rather than trusting queue-borne payloads (also the anti-spoofing posture), and authorize the intent against the fetched entity. Failed messages go to a DLQ after bounded receives; DLQ replay is an authenticated operator action.

**Outbox.** Domain events that must reach the queue reliably are written to an outbox table in the same transaction as the state change, relayed asynchronously. The relay is at-least-once; consumer idempotency absorbs duplicates. Prefer a **polling relay** (polling-publisher) as the portable default; DynamoDB Streams (transaction-log-tailing) is a permitted AWS-only latency optimization behind the same relay port, never surfaced to feature code. The app runs two or more replicas and has no in-process event bus, so any reaction that must reach another replica or survive a crash or restart goes through the queue or a publish-subscribe contract fed by this outbox ([plugin-architecture.md](plugin-architecture.md)). The first concrete consumer is the approval-workflow capability's cross-package step — the Access Sync result advancing an access request — a workflow continuation on the queue ([approvals.md](approvals.md)).

**Outbound retry** is owned by SDK-native configuration at client construction ([outbound-clients.md](outbound-clients.md)); consumers of `TRANSIENT_ERROR` decide whether to retry, honoring `retry_after` when present (queue consumers extend visibility timeout with it). Duplicate side-effects from ambiguous outcomes (timeout after the call landed) are absorbed by — again — consumer idempotency.

**Durable retry & circuit breaking.** Durable retry is not a second queue: it is built on `QueueService` (at-least-once + DLQ + visibility-timeout backoff, TASK-34) when a consumer first needs it, with a keyed store only for the SQS-inexpressible residue — scheduled/delayed retries beyond SQS's 15-minute `DelaySeconds`. The hand-rolled DynamoDB `RetryStore`, its worker and `ResilienceService` had no production consumer and are deleted, not migrated (TASK-111.13.2). A **circuit breaker**, when a consumer needs one, is deliberately **per-replica in-process** state — each replica trips on its own local health signal; it is *not* shared coordination and must not be moved onto the conditional-write store; the unused one in `infrastructure/resilience/` is deleted with it.

**Background jobs.** In-process, hookspec-registered, wrapped in an error boundary so one job's crash never kills the scheduler. **The scheduler is a clock-driven host capability, composed like a transport** ([platform-transports.md](platform-transports.md)): the host owns the runtime — the schedule loop, the `safe_run` error boundary, shutdown, and Tier-2 lease enforcement — while each feature *pushes* its own job at startup through the `register_background_jobs` hookspec ([plugins.md](plugins.md)), carrying its schedule, Tier classification, and (Tier-2) lease TTL from the feature's own partitioned settings ([configuration.md](configuration.md)) — exactly as a feature pushes a router through `register_routes`. The host never hand-imports feature job bodies; the legacy pull-hub that does (`app/jobs/scheduled_tasks.py::init`) is a tolerated divergence, strangled job-by-job as each `modules/` job migrates to a package, and the widened registry Protocol that lets features declare tier/TTL/schedule declaratively is the mechanism. The scheduler's *own* two jobs — the heartbeat and the integration health-check sweep — are host-owned Tier-1 and stay in the capability. A single scheduler-owned **default** lease TTL covers not-yet-migrated `modules/` jobs; per-job TTLs are feature-partitioned, never a central `jobs/settings.py` aggregator with one field per job. Tier-1 jobs are safe to run concurrently on every replica; a Tier-2 (singleton) job runs once across replicas by taking a TTL lease from the coordination contract (the same conditional-write primitive) — and the lease is a duplication *optimization*, never a correctness mechanism: the job body must be idempotent regardless. Jobs join shutdown within the lifespan's budget. The lease semantics live in the `LeaseStore` facade (`app/contracts/coordination/lease.py`), the one place acquire/release over the primitive is implemented; `build_lease_store(in_progress_ttl_seconds)` and the per-TTL `get_lease_store` in `app/infrastructure/coordination/factory.py` build it with a lease-specific TTL, and the host's lease enforcement `run_if_leased` stays in `app/infrastructure/coordination/lease.py`. Features and the scheduler consume the facade and never reimplement acquire/release semantics locally. Because over-run takeover is acceptable (not a correctness break) per the idempotent-job-body mandate above, no lease-renewal/heartbeat capability is needed; the ownership rule above guarantees only that the overrun holder's release cannot free the new holder's lease: each Tier-2 lease's TTL is sized to that job's own expected max run duration (never reused blindly from the generic dedup store's short in-progress TTL default), the same sizing choice already made for the Access Sync platform/user lock. If a caller also needs "who currently holds this" reporting, that is a distinct, best-effort keyed-record capability (own small store over the generic `RecordStore`, e.g. Access Sync's `JobStatusStore`) — never the deleted legacy idempotency cache, and never folded into the lease's own correctness gate.

**The scheduler has a run switch, like a transport.** `[scheduler] enabled` in the configuration files decides whether the scheduler starts on this deployment (false in base, true in production), never an `ENVIRONMENT` comparison ([configuration.md](configuration.md), TASK-112.4). It starts in the transport phase independent of every transport ([lifecycle.md](lifecycle.md)): it never waits on, or receives, the Slack runtime. A job that calls a vendor takes that vendor's outbound client ([transport-slack.md](transport-slack.md): outbound-only callers use the Web API client, never the runtime) and is scheduled only when the vendor's tenant entry is configured, logging the skip otherwise.

## Consequences

- One primitive (conditional write) backs dedup, leases, and outbox claims — one thing to implement correctly per backend, and it ports (Redis `SET NX`, Postgres unique insert, Cosmos conditional).
- Conflating dedup, locking, and job-status polling under one `get`/`set` cache reproduces the TOCTOU race in a new place and hides three call sites that need three different fixes behind one rewrite; migrating the store requires triaging each caller by which capability it actually needs, not a mechanical `get`→`claim`/`set`→`complete` rename.
- Consumers do more work (re-fetch, idempotency check) than a trust-the-message design; that work is the price of correctness under redelivery, and it is not optional.

## Checks

- Idempotency tests: two concurrent identical requests → one execution (asserted via the conditional-write path, not timing); redelivered message with different framing → same key.
- Conformance tests on every implementation: a stale holder's `release`/`complete` after a takeover returns `False` and leaves the new holder's record; `release` never deletes a `COMPLETED` record.
- Facade tests: an `INDETERMINATE` claim under `FAIL_CLOSED` leaves a lease unacquired and gives a dedup caller `IN_PROGRESS` with no token; each facade's policy is a required constructor argument with no default.
- grep: no `get(` -then-`put` patterns in the idempotency store; no "exactly-once" claims in code or docs.
- DLQ alarm exists; replay path requires an authenticated principal.
- CI check (`bin/check_settings_key_ownership.py`): no flat settings `enabled` switch and no `ENVIRONMENT` comparison decides whether a plugin or the scheduler runs (TASK-112.4).
- Boot test: with `[scheduler] enabled` the scheduler starts with the Slack transport off or failed.
