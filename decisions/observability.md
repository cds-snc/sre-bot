# Observability

## Context

The pieces exist separately today — structlog is configured with UTC timestamps and redaction installed, a correlation helper exists but no middleware calls it, and uvicorn/stdlib logs bypass the pipeline entirely. This record merges the three concerns because they only work as one pipeline.

## Decision

**Logging:** structlog, JSONL to stdout, one processor chain: level filter → `merge_contextvars` → logger name → UTC ISO timestamps → callsite → exception rendering → **redaction** → JSON render. Stdlib/uvicorn logs route through `ProcessorFormatter` with a matching foreign chain — one shape for the whole stream. Levels: DEBUG diagnostics, INFO state changes, WARNING degraded-but-handled, ERROR failed work, CRITICAL boot-fatal (`plugin_boot_failed` names the plugin, phase, error type and the setting at fault (`setting` field), [plugins.md](plugins.md)). A failed boot credential check is ERROR (`credential_check_failed`), an inconclusive one WARNING ([lifecycle.md](lifecycle.md)).

**Service identity on every record.** A processor right after `merge_contextvars`, in both the structlog and the foreign chain, adds the OpenTelemetry resource attributes, built once in the configuration phase: `service.name` (the distribution name from the package metadata, one source, no setting), `service.version` (`GIT_SHA`), `service.instance.id` (a random UUID v4 per process, the OpenTelemetry recommendation, so no platform name joins [configuration.md](configuration.md)'s closed list) and `deployment.environment.name` (`ENVIRONMENT`). They are resource attributes, the same on every record from one source, not request context, so they are not bound to contextvars, which `clear_contextvars()` empties ([OpenTelemetry service attributes](https://opentelemetry.io/docs/specs/semconv/resource/service/), [logs data model](https://opentelemetry.io/docs/specs/otel/logs/data-model/)). Log field names follow the OpenTelemetry semantic conventions wherever one exists (`code.file.path` already does), as flat dotted keys, so an OTLP exporter later maps them without loss. No separate identity event is logged: every record already carries it. The startup configuration report is [configuration.md](configuration.md)'s.

**Log destinations.** The JSON stream goes to the CloudWatch log group `/ecs/sre-bot-app`, kept 30 days (`terraform/ecs.tf`), with no subscription filter; Sentinel receives only audit events, through the audit sink. A new destination is recorded here before it is added, because a value's place in logs is judged by who can read every destination ([ASVS 5.0](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x25-V16-Security-Logging-and-Error-Handling.md) 16.2.3 log inventory, [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) on third parties). Read access to the log group is the AWS account's IAM, outside this repository.

**Logging starts in the configuration phase.** The app factory configures this pipeline right after the identity and `[logging]` slices load, before any other slice validates, so configuration-phase events render like every other line ([lifecycle.md](lifecycle.md)). A configuration-phase failure is logged once as `configuration_invalid` at CRITICAL, naming each key and the reason, never its value; the raised error carries no input value and no chained validation error, because pydantic renders every input, secrets included, into its message and key-name redaction never sees free text. uvicorn's loggers (`uvicorn`, `uvicorn.error`, `uvicorn.access`, `uvicorn.asgi`) lose their own handlers and propagate to the root handler when the pipeline is configured, so every line uvicorn writes after the app factory starts renders through it. A bootstrap pipeline (production JSON at INFO, default `[logging]` values, no service identity, since identity or `ENVIRONMENT` may be what failed) is installed first in the factory, so a failure before `[logging]` loads is one CRITICAL JSON line. uvicorn catches only `TypeError` from the factory call and lets any other exception reach Python's default hook, which prints a raw traceback ([uvicorn `config.py`](https://github.com/encode/uvicorn/blob/master/uvicorn/config.py)); a `sys.excepthook` therefore renders an escaping exception as one CRITICAL `uncaught_exception` event and skips a configuration failure already logged as `configuration_invalid` ([sys.excepthook](https://docs.python.org/3/library/sys.html#sys.excepthook)). Lines that stay plain: uvicorn's own 'Error loading ASGI app' import message, the reload supervisor's lines in local development, Python warnings raised at import, and structlog events emitted while modules import (the webhook pattern lines, until TASK-168).

**Exceptions render once.** A traceback appears only inside the structured event (the JSON `exception` field) — never also as raw multi-line text on stdout/stderr. `ProcessorFormatter` renders `exc_info` into the event once and then clears `record.exc_info`/`exc_text` (`keep_exc_info=False` is the default); a competing root handler that still calls `logging.basicConfig(format="%(message)s")` re-appends `formatException` after the JSON line, producing the duplicate. The gap is closed (TASK-28.2).

**Alerting keys on structured fields, never on free text.** Metric filters and alarms match JSON fields in the log body (`{ ($.level = "error") || ($.level = "critical") }`, `{ $.event = "..." }` — values are case-sensitive and structlog renders levels lowercase), not a substring/regex over the raw line ([CloudWatch Logs filter pattern syntax](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/matching-terms-json-log-events.html)). Level-less raw lines — dangling tracebacks, uvicorn's plain-text access lines — inflate a free-text alarm the moment they slip through. Expected-volume events must not be bumped to WARNING just to make a text filter see them; WARNING still means degraded-but-handled, per the level definitions above. A skipped feature or a failed credential check leaves the deploy green, so the error alarm is what reports it; those events must never be downgraded below ERROR. uvicorn access lines are INFO whatever the status, so a free-text error filter does not count a 5xx response; failed work is counted from the application's error events and uvicorn's `Exception in ASGI application` (ERROR) until TASK-94 matches fields (a 5xx metric on `$.logger = "uvicorn.access"` is TASK-94's).

**Health-check traffic is classified, never dropped.** `/version`/`/health` are polled by the ALB target group and the Route53 health check ([health-checks.md](health-checks.md)), which is expected, already-budgeted background volume — not a defect to silence. Per OWASP's logging guidance, known monitoring traffic must never be excluded from logs, only flagged. Once uvicorn access logs route through the pipeline (TASK-28), a narrow `logging.Filter` on `uvicorn.access` downgrades **exact** liveness-check hits (`GET`, path in `{/version, /health}`, status `200`, no query string) to DEBUG or tags them `event_type=healthcheck`; any other method, status, path, or query string on those routes logs unchanged at INFO+, so probing/fuzzing stays visible. The filter sits on the `uvicorn.access` logger, reads the record's args, re-levels an exact hit to DEBUG and emits it only when DEBUG is enabled, as `logger.debug` would: a handler without a level would otherwise emit the re-levelled record (TASK-28.2 chose DEBUG over the tag).

**Redaction:** a deny-list, key-name-based processor (`token`, `secret`, `password`/`passwd`/`pwd`, `authorization`, `api_key`, `credentials`, `signature`, `session*`, `*_token`…) that **recursively** walks nested dicts/lists, replacing values with `***REDACTED***`. Installed in the chain, so it cannot be skipped per-call. Extension via a `redaction_extra_keys` setting. Redaction of key-named fields is the enforceable guarantee; not logging secrets in free-text messages remains a review rule (don't interpolate payloads into message strings).

**Failure logs carry diagnostic shape, not payloads.** When an outbound call fails on a payload we built or rewrote (for example a Slack `invalid_blocks` rejection), log the provider's error code/details plus the payload's shape — counts, offending index, field lengths, before/after our own transformations — never the payload text itself. This is the same boundary as the review rule above, applied to failure paths specifically: diagnose from shape, not content.

**Correlation:** one ASGI middleware, first in the stack: accept a valid inbound `traceparent`/`X-Request-ID`, else generate a UUIDv4; **bind it to `contextvars` as `request_id`** (one name, everywhere); echo `X-Request-ID` on responses; include it in problem-details bodies. Malformed inbound IDs are silently replaced (injection defense). Platform transports bind the same key at their inbound boundary; queue messages and outbox events carry it so consumers re-bind it. `request_id` is correlation only — it changes on every redelivered request and is **never** used as an idempotency key ([reliability.md](reliability.md)).

The audit trail for security events (auth failures, dev-bypass use, authz denials) uses the same pipeline with a dedicated logger name — separable downstream without a second stack.

## Consequences

- `grep request_id=<id>` reconstructs a request across HTTP, Slack, events, and queue consumers — the actual payoff of all three pieces landing together.
- Key-name redaction can't catch secrets in prose; we accept that boundary and enforce the half that's enforceable.

## Checks

- Pipeline test: a nested `{"config": {"api_token": "x"}}` logs as redacted; uvicorn access line renders as JSON.
- Middleware tests: generated/echoed/forwarded/malformed `X-Request-ID` cases; `request_id` present on a log line emitted inside a route.
- Timestamps are UTC ISO-8601 on every line, structlog-native and foreign (stdlib/uvicorn); UTC is set explicitly (`TimeStamper(fmt="iso", utc=True)`), not inherited from the library default ([`structlog.processors.TimeStamper`](https://www.structlog.org/en/stable/api.html#structlog.processors.TimeStamper) defaults `utc=True`, but the default must not be relied on silently).
- An exception logged in production mode (JSON renderer) yields exactly one line across stdout and stderr — no raw `formatException` text trailing the structured event (the stdlib root handler writes to stderr, where the duplicate was reproduced).
- A subprocess test launches `uvicorn --factory` and asserts every output line is one JSON object, including a failure before `[logging]` loads and an exception escaping the factory.
